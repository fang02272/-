## 三、6G 定位参数设计（工艺建议，最终以真值标定为准）

### 3.1 基本定位
- 6G = **45° 固定管全位置焊**：管子固定不转，焊枪绕管壁完成一整圈
- 分段策略：**6点 → 12点 → 6点 两个半圈**（每半圈一次起弧/收弧，减少接头缺陷）；半圈内位姿连续变化

### 3.2 钟点分区建议（每半圈 6点→12点）

| 钟点区间 | 主导位姿 | 焊枪工作角建议 | 电流修正（相对平焊基准） |
|---|---|---|---|
| 6点 ± 15° | 仰焊（底部） | 85-95° | **-10 ~ -15%** |
| 7点 ~ 9点 | 斜仰 → 斜立 | 75-85° | -5 ~ -10% |
| 9点 ~ 11点 | 斜立 → 斜平 | 65-80° | 基准 ~ -5% |
| 11点 ~ 12点 | 斜平 → 平焊（顶部） | 60-75° | 基准 |

> 说明：上表为工艺惯例档位（设计建议），具体数值以 PR #4 真值表中的"位置段/方向 + 电流(A)"为准做插值/分段取整。

### 3.3 层道规划建议
- **打底层**：全位置电流修正（按上表钟点分区），保证根部熔透且不烧穿
- **填充/盖面层**：分道按半圈规划，**相邻层接头错开 ≥1/4 圈**（避免接头重叠缺陷）
- 卡片中表达为 `pass_sequence` 扩展（每层 × 每钟点区间的参数段），板材工况保持现有按板厚逻辑不变

## 四、数据接口设计

### 4.1 数据源（待合入校准）
- **首选数据源：队友 PR #4 的 `data/pipeline_6g_data.json`**（43 条），字段（以 PR 实际内容为准）：
  `母材/钢级、管径、壁厚、焊接位置、位置段/方向、焊道、焊接方法、焊材型号及直径、保护气体及流量、电流(A)、电压(V)、焊接速度、焊枪/焊条角度、预热/层间温度、来源`
- ⚠️ 该表 schema 与 `weld_cases.json` 的 15 键英文结构不同，**接入前需字段映射或转换**（见 4.2）

### 4.2 入库方案（两案择一，建议 A）
- **方案 A（建议）：并入 weld_cases.json**，新增：
  - `joint` 枚举扩充：`"6G45°固定管"`、`"5G水平固定管"`、`"2G垂直固定管"`
  - 材料归一化：`钢管 = 碳钢管/不锈钢管`（材料 × 管形 二维，不破坏现有板材条目）
  - 可选新键：`pipe_diameter_mm`、`groove_angle`、`root_gap`；复用现有 `variant` 机制（基准/电流大/…）
- 方案 B：保留独立 6G 表，`find_weld_case` 增加管道第二查询入口（管道工况先查 6G 表、未命中再回退通用表）——文件多一个、逻辑两套，仅当数据量级增大（数百条）时优先

### 4.3 代码扩展点（本次不动，实施时按此清单改）
| 扩展点 | 位置 | 改动内容 |
|---|---|---|
| 材料归一化 | `robot_welding.py:225` | 增加 钢管/碳钢管/不锈钢管 → 管道材料键 |
| 接头归一化 | `robot_welding.py:241` | 增加 6G/5G/2G/45°固定管/水平固定管 → 位号键 |
| 取数入口 | `robot_welding.py:280` | find_weld_case 支持管径/位号维度（或新增 find_pipe_case） |
| 卡片电参数消费 | `process_card.py:288-294` | 6G 真值按"位置段"取段参数，替换整段单值覆盖 |
| 枪姿/摆幅消费 | `process_card.py:368-382` | gun_pose/weave_* 支持按钟点分段真值 |
| 卡片输出 | `process_card.py` robot 块 | 扩充 `robot.pipe`：`{pipe_mode, position_code:"6G", angle_deg:45, segments:[{clock_range, posture, current_adj, …}]}`；板材工况保持 `pipe={}` 向后兼容 |

### 4.4 查询结构化（识别层建议）
- 现管道判定纯关键词 → 建议升级为：问句经 6G/5G/45°/固定管 信号归一 → 输出 `position_code` + 可选的管径数值，传入卡片链路
- 示例：`"45°固定管6G怎么焊"` → `{is_pipe:true, pipe_fixed:true, position_code:"6G"}` → 命中 6G 分段真值

## 五、性能评估

| 项 | 现状 | 6G 接入后预估 |
|---|---|---|
| 真值文件 | weld_cases.json 388KB / 1340 条，懒加载 + 进程内存缓存 | +43 条 ≈ +3%（方案 A）或独立文件 733 行 ≈ 50KB（方案 B） |
| 取数扫描 | `find_weld_case` O(n) 线性扫描 + 板厚最近邻，≤2 次（目标档 + 基准回退） | 1400 条内单次扫描 <1ms 量级，总耗时 <5ms |
| 卡片构建 | 数据查找 + 规则组装（纯 dict）≈ 10ms 级 | 分段参数只多一次 dict 索引，+1~2KB JSON，仍 <50ms 预算 |
| 响应链路 | 卡片就绪 → 跳过 LLM 直接本地返回（server.py:796-799） | 6G 卡片保持纯本地路径，响应时间 <1s 目标内 |
| 渲染 | 前端按字段渲染表格/徽标 | robot.pipe.segments 为列表，前端遍历渲染，无压力 |

## 六、实施阶段建议

1. **Phase 0（前置）**：PR #4 合入 main → 按实际数据校准本文档 4.1 字段名
2. **Phase 1**：归一化扩展（_normalize_material / _normalize_joint）+ 取数入口（robot_welding）
3. **Phase 2**：卡片消费端映射 + `robot.pipe` 结构化输出（process_card）——顺手修正 `_pipe_strategy` 的 seg1/seg2 方向文案矛盾
4. **Phase 3**：钟点分区参数（打底/填充/盖面层道）按 4.2 方案 A 落表
5. **Phase 4**：验证——管道真值用例集 + `tools/tests.py` 全量回归 + 卡片字段断言测试
